# 運用手順

## 環境

| 環境 | ポート | コンテナ名の接頭辞 | 用途 |
| --- | --- | --- | --- |
| 開発 | 8888 | `wp-env-museum-calendar-<ハッシュ>-` | 手動確認。`npm run setup` / `npm run dev` |
| テスト | 8889 | `wp-env-museum-calendar-test-<ハッシュ>-` | 自動テスト。`npm run check` などが起動 |

- 各環境は `wordpress`（Apache+PHP）、`cli`（WP-CLI・Composer）、`mysql`（MariaDB）の3コンテナで、DBも環境ごとに別です。
- 稼働状況は `docker ps --filter name=wp-env-museum-calendar`、Apache/PHPの出力は `docker logs <wordpressコンテナ名>`、WordPressのデバッグログはコンテナ内の `wp-content/debug.log` で確認します。
- 基準は `.wp-env.json` です。`.wp-env.test.json` と `.cache/wp-env` は生成物なので編集しません。
- DBはDockerのボリューム（`wp-env-museum-calendar-…_mysql`）にあり、`npm run stop` では消えません。

### 別の端末から開く

WordPressはリンクやCSSのURLをサイトURLから生成するため、`localhost` 以外の名前で開くにはサイトURLの変更が必要です。
Git対象外の `.wp-env.override.json` に次のように書き、`npm run dev` で反映します（ポートは自動で付きます）。

```json
{
  "config": {
    "WP_SITEURL": "http://<ホスト名>",
    "WP_HOME": "http://<ホスト名>"
  },
  "lifecycleScripts": {
    "afterStart": "docker exec -u root \"$(docker ps -q --filter 'name=^wp-env-museum-calendar-[0-9a-f]+-wordpress-1$')\" sh -c \"grep -q ' <ホスト名>$' /etc/hosts || echo '127.0.0.1 <ホスト名>' >> /etc/hosts\""
  }
}
```

`afterStart` は、コンテナ内からそのホスト名を解決できるようにします。これがないとWordPressが自サイトへ接続できず、WP-Cron（ICSの定期取得）が動きません。
テスト環境はこの上書きの影響を受けず、`localhost:8889` のままです。

## WordPress・PHPの更新

1. `npm run check:updates` でWordPressの公開版を確認。
2. 変更用ブランチで `.wp-env.json` のcore URLまたはphpVersionを変更。
3. `npm run setup` と `npm run check` を実行。
4. 必要に応じて `npm run wp -- core update-db` で開発DBを更新。

これはローカルのコンテナの更新です。本番の更新、バックアップ、配備は自動化していません。
**旧版から新版へのDB移行テストは未実装**です。本番を更新する前に、旧版のDBを複製して新版へ移行する検証を追加してください。

## ステージングへの配備

mainへのpushで「Calendar checks」が成功すると、「Deploy to staging」（`.github/workflows/deploy-staging.yml`）がそのZIPをステージングのWordPressに配備します。

- 配備先はリポジトリ変数 `STAGING_URL`。現在の値は[開発の手引き](development.md#ステージング)にあります。
- ログインはシークレット `STAGING_WP_USER` と `STAGING_WP_PASSWORD`。ログイン情報はリポジトリに書きません。
- `scripts/deploy-staging.mjs` がPlaywrightで管理画面にログインし、「プラグインのアップロード」でZIPを上書きして有効化します。
- 続けて、プラグインのVersion、カレンダーの登録状況、「今すぐ更新」の成否、トップページの月間カレンダーと本日の予定を確認します。どれかが満たされないと失敗し、画面の画像を `staging-failure` として残します。設定ページは保存したURLを表示しないため、この画像に非公開URLは写りません。
- 手元から実行するには、`npm run package` の後に `STAGING_URL=… STAGING_WP_USER=… STAGING_WP_PASSWORD=… node scripts/deploy-staging.mjs dist/museum-calendar-<版>.zip`。
- 配備先を変えるときは、変数とシークレットを `gh variable set` と `gh secret set` で更新します。確認はトップページに両方のショートコードがある前提です。

### 実サイトのトップページの写し

ステージングのトップページは、旧古河邸サイトのトップページの写しです。本日の予定とカレンダーだけを出します（作り方は[開発の手引き](development.md#実サイトのトップページ)）。テーマは `otani-museum2026`、フロントページは固定ページ `top` です。

- mainへのpushで配備されるのはプラグインだけです。テーマはGit対象外なので、変えたら手元から配備します。
- `npm run site:package` が `dist/site-theme-otani-museum2026.zip`（テーマ）と `dist/site-seed.zip`（ページ設定のプラグイン）を作ります。
- `npm run site:deploy` は、テーマのZIPを作り、ステージングの「テーマのアップロード」で上書きします。続けて、配信されるテーマのJavaScriptとCSSが手元と同じこと、テーマが有効なこと、`/` と `/en/` にカレンダーと本日の予定があることを確認します。テーマを有効にする操作はしません。失敗すると画面の画像を `test-results/staging-failure.png` に残します。
- ログイン情報は `STAGING_URL`、`STAGING_WP_USER`、`STAGING_WP_PASSWORD`。Git対象外の `.env` に書くか、環境変数で渡します。環境変数が `.env` より優先します。
- `npm run site:deploy` が使えないときは、管理画面の「テーマのアップロード」でテーマのZIPを上書きします。
- ページを作り直すときだけ、`site-seed.zip` を「プラグインのアップロード」で入れて有効化します。有効化のときにテーマを有効にし、固定ページ `top` と `en` の不足分だけを作ります。既存のページは変えません。作成後は無効化します。
- 元に戻すには、テーマをTwenty Twenty-Fiveに切り替え、「設定 → 表示設定」でフロントページを元のページに戻します。

## 予定の登録

職員がGoogleカレンダーに予定を登録するときのルールです。サイトに載せる予定だけを入れる専用のカレンダーを使います。カレンダー自体は非公開でも、登録した予定は説明欄を含めてすべてサイトで公開されます。

### タイトル

タイトルは「設定 → Museum Calendar」の「予定の種類と英語での表示」の表から選び、表のとおりに入力します。プラグインはタイトルから予定の種類を決めます。次の8つは既定の表です。サイトの管理者が表を変えていれば、画面の表に従います。

| タイトル | 使う場面 | 英語のページでの表示 |
| --- | --- | --- |
| `開館日` | 開館日 | `OPEN` |
| `休館日` | 休館日 | `CLOSED` |
| `お茶室営業日` | お茶室の営業日 | `Tea Room Open` |
| `ガイドツアー開催日` | ガイドツアーのある日 | `Guided Tour` |
| `結婚式` | 結婚式のある日 | `Wedding` |
| `夜間特別開館` | 夜間の特別開館 | `Special Evening Opening` |
| `コンサート` | コンサートのある日 | `Concert` |
| `イベント` | そのほかの催し | `Event` |

- 全体が一致したときだけ、その種類になります。`開館`、`臨時休館日`、`開館日（午後）`、`開館 日` は別のタイトルです。前後の空白は無視します。
- 催しの固有の名前（例: アフタヌーンコンサート）はタイトルに入れず、説明欄に書きます。

### 開館日と休館日

- `開館日` は時刻付きで登録します（例: 10:30〜16:30）。サイトの開館時間は、この予定の時間です。終日で登録すると、開館時間が出ません。
- `休館日` は終日で登録します。
- 通常の開館日は、1日ずつ入力せず繰り返し予定にします（例: 毎週火曜〜日曜の10:30〜16:30）。繰り返しは何回でも1件と数えます。
- 臨時休館は、その日に終日の `休館日` を足します。同じ日の `開館日` は削除しなくても、サイトには `休館日` だけが出ます。
- 開館時間がふだんと違う日は、繰り返しの `開館日` のその日だけを開き、「この予定」だけ時間を変更します。
- `開館日` も `休館日` もない日は、サイトに開館状況が出ません。休館とも表示しません。

### 説明欄

- 催しの名前、内容、申し込み方法などを書きます。テーマが、日付を押したときに出るその日の予定の一覧に表示します。
- 説明欄は公開されます。内部の連絡や個人の名前は書きません。
- サイトで使うのは書式を外した文字だけです。太字やリンクの書式は外れ、改行は残ります。
- 予定の名前を詳しいページへのリンクにするには、そのページのURL（`https://` から）を説明欄の1行に単独で書きます。その行は説明として表示しません。
- 文中に書いたURLは文字のまま残り、リンクになりません。URLだけの行が2行以上あると、リンクになるのは最初の行だけです。
- 繰り返し予定では、繰り返しの予定全体（「すべての予定」）に書くと、すべての日にリンクが付きます。
- 500文字を超える分は省きます。
- 場所、ゲスト、添付ファイルはサイトに出ません。

### 表にないタイトルを使ったとき

- 予定はサイトに出ますが、表の色もテーマの種類ごとの色も付きません。英語のページでも、登録したタイトルのまま日本語で出ます。
- 該当するタイトルは、「設定 → Museum Calendar」の「種類が未定義の予定名」に並びます（今月から12か月分）。
- 入力の誤りならGoogleカレンダーでタイトルを直します。新しい種類が要るなら、サイトの管理者が同じ画面の表に行を足して保存します。

### 登録の後

- サイトへの反映は約15分ごとです。すぐに確かめるには「設定 → Museum Calendar」の「今すぐ更新」を押します。
- 1か月分を登録したら、サイトの月間カレンダーで翌月まで送り、開館日、休館日、催しの日を確かめます。

## 本番サイトの切り替え

旧古河邸サイトのトップページ（日本語 `/` と英語 `/en/`）のカレンダーを、今のカレンダーのプラグイン（管理画面への手入力）からMuseum Calendarに切り替える手順です。
本番の変更は、ローカルとステージングの検証とは別の作業です。先にステージングで、切り替えと復旧を1回ずつ通します。

### 切り替えの前

1. 本番のファイルとDBをバックアップし、復元できることを確かめます。Museum Calendarを登録した後のDBのバックアップには、非公開URLの秘密の部分が平文で入ります。保管場所と共有範囲をパスワードと同じ扱いにします。プラグインを削除しても、削除前のバックアップからは消えません。
2. 今のテーマをZIPで保存します。元に戻すときに使います。
3. 本番用のGoogleカレンダーを作ります。「設定と共有 → 予定のアクセス権限」の「一般公開して誰でも利用できるようにする」はオフのままにし、「特定のユーザーまたはグループと共有する」で予定を登録する職員のアカウントを追加します。「カレンダーの統合」に「iCal形式の非公開URL」が出ることを確かめます。出ない場合は[非公開URLが使えないとき](#非公開urlが使えないとき)を参照します。
4. [予定の登録](#予定の登録)のとおりに、当月と翌月以降の予定を登録します。今のサイトのカレンダーと日ごとに見比べます。
5. ページキャッシュ（プラグイン、サーバー、CDN）を使っているかを確かめます。使っている場合は、トップページ `/` と `/en/` のキャッシュ時間を15分以下にするか、対象から外します。長いままだと、本日の表示が前日のまま残ります。

### 切り替え

今のカレンダーのプラグインは、最後の手順まで有効のままにします。

1. 「プラグイン → プラグインを追加 → プラグインのアップロード」で、Museum Calendarの配布ZIP（GitHub Releasesの `museum-calendar-<版>.zip`）を入れて有効化します。この時点では、サイトの表示は変わりません。
2. 「設定 → Museum Calendar」に、本番用のカレンダーの「iCal形式の非公開URL」を登録します。URLはGoogleカレンダーの画面から直接コピーして貼り付け、メールやチャット、作業メモに残しません。保存と同時に予定を取得します。「登録状況：非公開URLを登録済み」と、「取得状況」に最終取得の日時が出ることを確かめます。「種類が未定義の予定名」が出ていれば、意図しないタイトルがないことも確かめます。
3. テーマを更新します。ステージングで確かめたテーマから、次を本番のテーマに入れます。
   - トップページのテンプレートで、今のカレンダーの出力を `[museum_calendar]` と `[museum_calendar_today]` に置き換える変更。英語のページは `lang="en"` を付けます。
   - `museum-calendar/month.php` と `museum-calendar/today.php`（カレンダーと本日の表示のマークアップ）。
   - 種類ごとの色、予定のリンク先、日付を押したときの予定の一覧（CSS、JavaScript、`functions.php` から読み込むファイル）。
4. ページキャッシュを消去します。
5. [切り替えの後の確認](#切り替えの後の確認)を行います。
6. 問題がなければ、今のカレンダーのプラグインを無効化します。削除はしません。手入力した予定のデータはDBに残ります。

### 切り替えの後の確認

日本語 `/` と英語 `/en/` の両方を、PCとスマホで確かめます。

- 本日の表示が、Googleカレンダーの当日の `開館日`（開館時間）または `休館日` と合っている。英語のページでは `OPEN` または `CLOSED` と出る。
- 月間カレンダーの当月が、Googleカレンダーと日ごとに合っている。種類ごとの色が付いている。
- 翌月と前月へ送れて、送った後もカレンダーの位置に戻る。
- 予定を押すと、名称、日付、時間、説明、リンクが出る。キーボードでも開閉できる。
- 英語のページで、月、曜日、予定のタイトルが英語になっている。
- スマホで、カレンダーの表と予定の時間が読める。
- ログアウトした状態（別のブラウザー）でも同じ表示になる。ページキャッシュが効いている場合の確認です。
- 翌日に、本日の表示が日付とともに変わっている。

### 元に戻す

予定のデータは消さずに、表示だけを戻します。

1. 今のカレンダーのプラグインを無効化していた場合は、有効に戻します。
2. テーマを、切り替えの前に保存したZIPで上書きします。
3. ページキャッシュを消去し、トップページに元のカレンダーが出ることを確かめます。
4. Museum Calendarは無効化します。設定（非公開URLの秘密の部分を含む）と取得済みの予定は残り、定期取得は止まります。Googleカレンダーの予定も残します。
5. Museum Calendarを使わないと決めたら、「プラグイン」で削除します。削除すると、設定（非公開URLの秘密の部分を含む）、予定の種類の表、取得済みの予定がDBから消えます。

- 切り替えの後に今のカレンダーのプラグインへ手入力していない期間の予定は、戻した後に手入力で補います。
- 再び切り替えるときは、Museum Calendarを有効化して「切り替え」の手順3から行います。

## 非公開URLの漏えいとリセット

非公開URLを知っている人は、カレンダーのすべての予定を読めます。メール、チャット、画面共有、スクリーンショット、課題管理、ログに出たときは、漏れたものとして扱います。

1. Googleカレンダーで本番用のカレンダーの「設定と共有 → カレンダーの統合」を開き、「iCal形式の非公開URL」の横の「リセット」を押します。古いURLはすぐに使えなくなります。
2. 新しい「iCal形式の非公開URL」をコピーし、「設定 → Museum Calendar」に貼り付けて保存します。秘密の部分が変わるので、取得済みの予定を消して取り直します。
3. 「登録状況：非公開URLを登録済み」と、「取得状況」に新しい最終取得の日時が出て「取得失敗」が出ていないことを確かめます。

- 手順1と2の間はサイトが予定を取り直せず、前回取得した予定を表示し続けます。間を空けずに行います。
- 「取得失敗」に、非公開URLのリセットやカレンダーの削除を確かめる案内が出ているときは、誰かがGoogle側でリセットした可能性があります。同じ手順2から登録し直します。
- 古いURLを含むDBのバックアップは、リセットの後は予定を読めませんが、引き続き保管の範囲を限ります。

### 非公開URLが使えないとき

Google Workspaceでは、管理者が「iCal形式の非公開URL」（非公開アドレス）を無効にできます。無効なら「カレンダーの統合」に表示されません。

- 組織のGoogle Workspace管理者に、このカレンダーの持ち主に対して非公開アドレスを許可するよう依頼します。
- 許可できない場合は、カレンダーを一般公開し、「すべての予定の詳細を表示」を選んで「iCal形式の公開URL」を登録します。URLを知らなくても誰でもカレンダーを読めるので、サイトに載せる予定だけを入れたカレンダーであることを確かめます。

## 予定の種類の表の復旧

表（オプション `museum_calendar_kinds`）は、既定の表から変えたときだけ保存されます。

- 既定の表に戻すには、「設定 → Museum Calendar」で「既定の表に戻す」をチェックして保存します。
- 管理画面を開けないときは、WP-CLIでオプションを削除します。削除すると既定の表に戻ります。

```sh
wp option delete museum_calendar_kinds
```

- 保存済みの値が読めないときは、プラグインが既定の表を使います。公開ページは止まりません。

## 依存関係

- PHP依存の更新はcliコンテナ内のComposerで行い、composer.jsonとcomposer.lockを同じ変更に含めます。
- `package.json` のoverrides（isomorphic-git、qs、rimraf）は、wp-env 12.1.0の間接依存に対する修正版の指定です。wp-envを更新するときに、外せるかを確認します。
- `renovate.json` を置いていますが、Renovateの接続は別途必要です。

## 予定の定期取得

WP-Cronはサイトへのアクセスで動きます。アクセスの少ないサイトで定刻に更新するには、サーバー側のcronからWP-Cronを実行します。

## 復旧・停止

- 停止は `npm run stop`、再開は `npm run dev` です。
- コンテナとボリュームを破棄する操作はデータを消すため、開発コマンドには含めていません。
- 本番DBの移行を伴う更新は、コードの差し戻しだけでは復旧できません。本番運用の前に、DBとファイルのバックアップと復元試験を整備してください。
